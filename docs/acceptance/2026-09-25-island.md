# Independent Dynamic Island mode: not accepted

The user reported that starting Osu Audio stopped broadcasting immediately with
“无法连接灵动岛字幕，请回到 Osu 重新开始”. Device logs collected at
2026-09-25 07:09 UTC show repeated `island/activity_unavailable`, followed by
`broadcast/ended`, including at 07:07:46 and 07:08:57 UTC. The host had connected
successfully but received no translations. This is a confirmed feature failure,
not an unresolved signing or user-permission problem.

## Simulator checks

Runtime: iPhone 17, iOS 26.5. All runs use disposable fixture credentials and
in-memory provider responses. No cloud requests or physical-device installs.

| Check | Result | What it establishes |
| --- | --- | --- |
| `--verify-island-in-process` | Passed | Activity creation, text/original updates, pause, immediate end within one app process |
| `test-island-processes.py` | Acceptance failed; isolation failure reproduced | Host creates a real activity; a second simulator application runs the production broadcast-side lookup and sees zero activities |
| `--verify-island-unavailable` | Passed | The known-broken mode stops before opening broadcast or creating a cloud session; explicitly switching to PiP still starts the normal flow |
| `--verify-capture-start` | Passed at 07:33:05 UTC | Existing 45-second permission wait, retry, cancellation, first audio, and final drain remain intact with fixture capture |

The Release simulator app build, TypeScript check, native core tests, Ruby syntax,
and diff checks also passed. One capture test invocation timed out because the
launched app lacked the requested test argument (verified from its process args).
The launcher now uses `--terminate-running-process`; rerunning with the verified
argument produced the fresh passing result above. The timeout was not counted as
a passed test. PiP rendering itself is unavailable in this simulator; the capture
fixture verifies the controller/transport path, not a rendered PiP window.

The process test records both PIDs and checks that they differ. It preserves the
actual failure as `acceptancePassed: false` and exits with status 1. It must not
be counted as successful feature acceptance just because reproduction succeeded.
It also reports `providerClientCreated: false` when lookup fails: no provider
client is created for an unusable activity.

The second process is a separate application, **not a ReplayKit extension**.
Therefore this probe validates process/bundle isolation and demonstrates why the
old same-process test was inadequate. The actual ReplayKit failure is established
by the earlier physical-device logs, not by this simulator probe. An ordinary
application process and the broadcast extension sandbox are not interchangeable.

## Containment

The application now explains that independent island mode is unavailable before
requesting a broadcast. The extension distinguishes unavailable activities from
invalid configuration and no longer tells the user to retry a deterministic
failure. PiP remains available through explicit selection; this does not silently
replace the requested independent mode with a PiP-backed mode.

The original feature still requires a different background-update design and
end-to-end acceptance. The UI prototype and test pipeline are retained for that
work. This update has not been installed on the user's phone, per their request
to test in the virtual environment first.

## Reproduction

Build the isolated simulator harness as documented in `scripts/test-simulator.sh`.
Then run:

```sh
python3 scripts/test-island-processes.py SIMULATOR_UDID
scripts/test-simulator.sh SIMULATOR_UDID --verify-island-in-process 25
scripts/test-simulator.sh SIMULATOR_UDID --verify-island-unavailable 25
```

The first command is expected to fail acceptance on the current implementation.
Results are in `.build/island-process-result.json`; successful local regression
tests do not override that failed acceptance result.

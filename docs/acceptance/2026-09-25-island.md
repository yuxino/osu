# Independent Dynamic Island mode: not accepted

The user reported that starting Osu Audio stopped broadcasting immediately with
“无法连接灵动岛字幕，请回到 Osu 重新开始”. Device logs collected at
2026-09-25 07:09 UTC show repeated `island/activity_unavailable`, followed by
`broadcast/ended`, including at 07:07:46 and 07:08:57 UTC. The host had connected
successfully but received no translations. This is a confirmed feature failure,
not an unresolved signing or user-permission problem.

## Simulator checks

Runtime: iPhone 17, iOS 26.5. All runs use disposable fixture credentials and
in-memory provider responses. No cloud requests or physical-device installs.

| Check | Result | What it establishes |
| --- | --- | --- |
| `--verify-island-in-process` | Passed | Activity creation, text/original updates, pause, immediate end within one app process |
| `test-island-processes.py` | Acceptance failed; isolation failure reproduced | Host creates a real activity; a second simulator application runs the production broadcast-side lookup and sees zero activities |
| `--verify-island-unavailable` | Passed | The known-broken mode stops before opening broadcast or creating a cloud session; explicitly switching to PiP still starts the normal flow |
| `--verify-capture-start` | Passed at 07:33:05 UTC | Existing 45-second permission wait, retry, cancellation, first audio, and final drain remain intact with fixture capture |

The Release simulator app build, TypeScript check, native core tests, Ruby syntax,
and diff checks also passed. One capture test invocation timed out because the
launched app lacked the requested test argument (verified from its process args).
The launcher now uses `--terminate-running-process`; rerunning with the verified
argument produced the fresh passing result above. The timeout was not counted as
a passed test. PiP rendering itself is unavailable in this simulator; the capture
fixture verifies the controller/transport path, not a rendered PiP window.

The process test records both PIDs and checks that they differ. It preserves the
actual failure as `acceptancePassed: false` and exits with status 1. It must not
be counted as successful feature acceptance just because reproduction succeeded.
It also reports `providerClientCreated: false` when lookup fails: no provider
client is created for an unusable activity.

The second process is a separate application, **not a ReplayKit extension**.
Therefore this probe validates process/bundle isolation and demonstrates why the
old same-process test was inadequate. The actual ReplayKit failure is established
by the earlier physical-device logs, not by this simulator probe. An ordinary
application process and the broadcast extension sandbox are not interchangeable.

## Containment

(Superseded later the same day by the [redesign](#redesign-extension-owned-activity-2026-09-25-later),
which re-enables the mode; kept for the record.)

The application now explains that independent island mode is unavailable before
requesting a broadcast. The extension distinguishes unavailable activities from
invalid configuration and no longer tells the user to retry a deterministic
failure. PiP remains available through explicit selection; this does not silently
replace the requested independent mode with a PiP-backed mode.

The original feature still requires a different background-update design and
end-to-end acceptance. The UI prototype and test pipeline are retained for that
work. This update has not been installed on the user's phone, per their request
to test in the virtual environment first.

## Redesign: extension-owned activity (2026-09-25, later)

The first design failed because `Activity.activities` is process-scoped: the
ReplayKit extension could never look up the host's activity. The redesign
removes the cross-process dependency. The extension now requests and owns its
own Live Activity when the authenticated configuration arrives; the host no
longer creates one, and `IslandConfiguration` no longer carries an activity
identifier. If creation fails (real-time activities disabled, or ActivityKit
refusing a request from the extension sandbox), the broadcast ends immediately
with guidance to switch to PiP. The pre-broadcast block, the
`--verify-island-unavailable` check, and the two-process lookup probe are
retired: the design no longer depends on cross-process lookup, so that probe
guards nothing. Starting a Live Activity from a broadcast upload extension is
undocumented; only a physical-device broadcast can decide it, so independent
mode stays experimental and unaccepted.

Simulator checks (iPhone 17, iOS 26.5; disposable fixture credentials; no cloud
requests or physical-device installs):

| Check | Result | What it establishes |
| --- | --- | --- |
| `--verify-island-in-process` | Passed | The production session creates its own activity, updates translated and original text, pauses, and ends immediately with a synthetic provider |
| `--verify-capture-start` | Passed at 08:02:15 UTC | The ordinary PiP flow keeps its 45-second permission wait, retry, cancellation, authenticated first audio, and final drain |
| `--verify-interactions` | Passed | Home actions, credential error/retry/removal, and original-text synchronization are unchanged |
| Release simulator app build | Passed | Host, MimiBroadcast extension, and OsuSubtitles widget compile with the redesign |

TypeScript, native core tests (now without an activity identifier in the
handoff), Ruby syntax, and diff checks also passed.

Remaining checks on the same phone, after the trust prompt is resolved:

1. Start island mode and authorize Osu Audio; diagnostics must show
   `island/extension_activity_started`, never `activity_request_failed`, and
   translations must keep updating after leaving Osu for at least two minutes.
2. Verify compact, expanded, and Lock Screen layouts and the original-text
   option.
3. Stop from Osu and from the system broadcast controls; verify activity
   removal and provider socket closure. Repeat after network loss and after
   dismissing the activity.
4. Repeat an ordinary PiP session to check real-device parity.

If the broadcast ends with the switch-to-PiP guidance, that outcome is a
definitive design answer about extension-created activities, not a signing or
permission problem. Until the device checks pass, README descriptions call the
mode experimental.

## Device verdict on the redesign (2026-09-25, later still)

The redesigned build was installed and the user exercised island mode the same
day. Extension diagnostics (session `96CCB87B…`) show the broadcast started at
12:05:53 UTC, the extension authenticated, decoded the configuration, and then
`Activity.request` threw the error recorded as `island/activity_request_failed`
with code 6. Decoded against the iOS 26.5 SDK interface, code 6 is
`ActivityAuthorizationError.visibility`: "The app tried to start the Live
Activity while it was in the background." Apple requires the process that
starts a Live Activity to be foregrounded; a broadcast upload extension never
is. The broadcast ended immediately with the switch-to-PiP guidance, so the
redesigned containment behaved as designed.

Both client-side handoffs now have physical-device evidence and both are ruled
out: the extension cannot look up a host-created activity (process-scoped
`Activity.activities`, 07:09 UTC), and it cannot start its own activity
(`.visibility`, 12:05:53 UTC). The one documented way for a non-app process to
start a Live Activity is an App Intent conforming to `LiveActivityStartingIntent`,
which requires a user-driven UI action and cannot be triggered from a broadcast
extension. Independent island mode is therefore not achievable without updating
the host-created activity through APNs `liveactivity` pushes, which requires a
backend component and is a product decision, not a client fix.

## Containment restored (2026-09-25, final)

The host again blocks island mode before opening the broadcast picker, now with
the accurate explanation: a Live Activity can only be created by a foreground
app, so the broadcast extension cannot create one. The extension-owned
implementation, the widget, and the in-process fixture are retained: they are
correct against ActivityKit and become usable if Apple relaxes the foreground
rule. Simulator checks (iPhone 17, iOS 26.5, fixture credentials, no cloud):

| Check | Result |
| --- | --- |
| `--verify-island-unavailable` | Passed at 12:13:13 UTC — island start explains "暂不可用" and stops before broadcast or cloud; PiP still starts |
| `--verify-capture-start` | Passed at 12:14:14 UTC — permission wait, retry, cancellation, authenticated first audio, and final drain unchanged |

TypeScript, native core tests, Ruby syntax, and diff checks passed. The
containment build replaces the experimental one on the device.

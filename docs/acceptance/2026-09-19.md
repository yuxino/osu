## Build 7 — restore the receiver after backgrounding

- Build 6 extension started at 13:52:48 UTC, timed out waiting for the host at 13:52:56 and stopped. The host had gone into the background when Mirroring closed, then returned to the foreground; it retained an apparently ready listener and never logged an accepted connection. The user confirmed seeing the timeout message asking them to start Osu even though they already had.
- The receiver did not recreate an idle listener after suspension. Apple's [networking lifecycle guidance](https://developer.apple.com/library/archive/technotes/tn2277/_index.html) and [Network framework clarification](https://developer.apple.com/forums/thread/840808) explain that an unadvertised listener can become stale without a failure callback. This is consistent with the observed failure; the logs do not independently prove kernel socket reclamation.
- Build 7 recreates the unconnected listener on foreground return, preserving a peer that is already attaching. A finite background task protects the broadcast-to-PiP handoff and is released on PiP start, cancellation, finish or expiration. If permission is still pending when the task expires, the listener closes and can be prepared again on foreground return. No idle audio/PiP activation was reintroduced.
- The extension logs waiting errors and retries a waiting local connection within the existing eight-second deadline. Timeout copy now says the connection failed instead of incorrectly implying the user skipped Start.
- The production-controller regression additionally exercised foreground-resume notifications before permission and after connection. At 14:00:43 UTC it passed the 45-second wait, cancel/restart, both PCM packets, connection preservation and confirmed finish. This tests lifecycle handlers with fixture input; actual iOS suspension remains a physical-device check. Signed Release build 7 and deep signature verification passed.
